# Wayfinder Onboard

Read `REPOSITORY.md` beside this file first, if it exists: it holds this repository's own rules for this skill, and they take precedence over the examples here.

## How this skill arrives
In a repository that does not run Wayfinder yet, this skill is installed by the kit's command: `pnpm add -D file:vendor/<tarball>` (a release's tarball, committed under `vendor/`: §3 step 1), then `pnpm exec wayfinder init` at the repository root. `init` installs this skill alone into the skills directory (`.agents/skills`, or its `--skills-dir`) and links it from `.claude/skills`. This run adds the root script `skills:install` (`node node_modules/@salientform/workspace-wayfinder/check/install-skills.mjs`, §3 step 3) and runs it to install the other skills (§3 step 5). Once the root `package.json` names `wayfinder.config`, `wayfinder init` installs nothing and points at that script, which owns the skills from then on. A repository that runs Wayfinder already uses this skill to switch an area on or off.

## Overview
Workspace Wayfinder is an engineering workspace a repository runs as its own small Vite app: areas for the roadmap and specs (Audit), READMEs, a feature catalogue, an API reference, plain-language docs and environments, each built from the repository's files at build time and kept true to the code by skills and check scripts. This skill fits it to one repository. It assumes JavaScript or TypeScript with Vite, and Node 22.18 or later (the checks load the `.mts` config directly). It asks before anything it cannot discover.

The templates beside this file (`templates/`) are the files to write. A `.tmpl` suffix (on the app's `package.json`, `tsconfig.json` and `vite.config.ts`, so no tool mistakes the templates for a project) is dropped when the file is written. `__NAME__` placeholders are filled from discovery:

| Placeholder | Means |
| --- | --- |
| `__PRODUCT__` | the product's name as its users know it |
| `__REPO_URL__`, `__BRANCH__` | the repository host's https URL (no trailing slash) and the branch links point at |
| `__WS__` | the workspace app's directory, repository-relative (`workspace`, or `apps/workspace` in a monorepo) |
| `__PACKAGE_NAME__` | the workspace app's package name, in a monorepo (`@acme/workspace`) |
| `__TO_ROOT__` | the path from `__WS__` back to the root (`..`, `../..`) |
| `__PORT__`, `__PREVIEW_PORT__` | the workspace dev server's and preview server's ports (the config's `ports`), assigned in §1 |
| `__TODAY__` | today, `YYYY-MM-DD` |

A template line ending in a marker comment, `[[with: <part>]]` (`// [[with: roadmap]]`, `# [[with: todo]]`, `/* [[with: tailwind]] */`), belongs to an optional part: keep the line, without the comment, when the repository has that part (§1, §2), and delete it when it does not. A `[[without: <part>]]` line is the other way round: kept, without the comment, only when the repository does not have the part. The parts are the Audit area's three optional files, `[[with: roadmap]]`, `[[with: todo]]` and `[[with: architecture]]`, and Tailwind v4 in the app, `[[with: tailwind]]` and `[[without: tailwind]]`. Only markers use `[[`, so once the files are written `grep -rn '\[\[with' <written files>` (and `\[\[without`) must find nothing.

## 1. Discover
Read, do not guess. Record each answer; they become the config.

| Question | Where to look | Decides |
| --- | --- | --- |
| Package manager, monorepo tool, workspaces | root `package.json` (`packageManager`, `workspaces`), `pnpm-workspace.yaml`, `nx.json`, `turbo.json` | install commands, `__WS__`, whether the app is its own package |
| Name, host URL | `package.json`; `git remote get-url origin`, written as https (`git@host:org/repo.git` → `https://host/org/repo`). The host of an SSH remote may be an alias from `~/.ssh/config` (`git@work-github:org/repo.git`): its real name is the `hostname` line of `ssh -G <alias>`; ask when that does not settle it | `__PRODUCT__`, `__REPO_URL__` |
| Branch | the branch work integrates into (where specs and plans merge), which can differ from `origin/HEAD`: ask when unsure | `__BRANCH__` |
| Ports | the repository's port rules (a port block, `.env`, a ports table), including any port register its instructions point to outside it, read for the ports already taken (§3 step 4 reports to the user, and does not edit, a register outside the repository) | `ports`: two free ports from the repository's own range, assigned now and never a framework default (3000, 3001, 4173, 4200, 5000, 5173, 8000, 8080). With no port rules, ask which ports to use |
| Other apps | the repository's other front ends (the product, a design system, docs) and their dev ports and deployed paths | `links`, the header's links to them (optional). The kit has no Design System area: a repository's design system is its own app, which `links` can point at |
| READMEs | the root README, package or library READMEs and how they group (`libs/`, `packages/`) | the `readmes` collection, `areas.readme.sections` |
| Tailwind | whether the repository uses Tailwind v4: `tailwindcss` 4 in a `package.json`, `@import 'tailwindcss'` in a stylesheet, `@tailwindcss/vite` in a Vite config | the part `tailwind`: with it, the app's `styles.css` compiles the kit's classes with Tailwind and the app's theme; without it, the app imports the kit's compiled stylesheet and installs no Tailwind |
| Router and navigation | the router setup (route tree, file routes), the sidebar or nav component | the Features route mirror; the rules file's `productRoutes` and `navLabels` |
| API | an OpenAPI 3 **JSON** document, or the command that emits one; where the product calls the API | the API area, `areas.api.generated`, `areas.api.callers` |
| CI | the repository's CI workflows, and whether anything that builds from the repository ignores `vendor/` or `*.tgz` (`.dockerignore`, a deploy tool's ignore file) | ask the user whether CI should run the check script (the committed tarball installs there: §3 step 1), and record the answer in this skill's `REPOSITORY.md` |
| Tests and coverage | test runners (Vitest, Playwright, `node:test`), test globs, coverage output (`json-summary`) | `areas.features.tests`, `areas.features.coverage` |
| Docs | the specs and plans directories (none yet: keep the defaults, `docs/specs` and `docs/plans`; the audit check accepts directories that do not exist yet, and a spec written there later is read); plain-language product docs; whether the repository keeps a roadmap, a TODO list or an architecture document in the kit's formats (`docs/formats.md`), or will start one: ask for each, since each is optional and a free-form file is not one of them | `specDirs`, Platform Docs; the parts `roadmap`, `todo`, `architecture` that `areas.audit` configures (§2) |
| Source layout | the source roots, entry files, libraries whose exports are a public API | `areas.features.sourceRoots`, `areas.audit.unusedExports` |
| Skills directory | where the kit's skills are installed: `.agents/skills` by default, the agent-neutral directory Codex and opencode read; another only when the repository already keeps its agent skills in one that every agent it uses reads | `areas.about.skillsDir`, the `skills` collection's globs |
| Agents | which coding agents the repository's people use (ask); where each reads skills (Claude Code `.claude/skills`; Codex `.agents/skills`, from the working directory up to the repository root; opencode `.opencode/skills`, `.claude/skills` and `.agents/skills`); whether git ignores each such directory (`git check-ignore -q <dir>/x`), and what for | `areas.about.skillLinks`: every agent directory that does not read the skills directory, each getting a link per kit skill (default `['.claude/skills']`, for Claude Code; `[]` when every agent reads the skills directory); for an ignored one, the narrower `.gitignore` rule in §3 |

## 2. Choose the areas
Readme, Audit and About always apply. The others only when the repository has what they read; leave an area out of `areas` rather than configure it empty.

| Area | Needs | Leave it out when |
| --- | --- | --- |
| Readme Index (`readme`) | READMEs | never |
| Audit (`audit`) | the reviews folder and each spec's and plan's front matter; and, each optional, a roadmap, a TODO list and an architecture document in the kit's formats (`node_modules/@salientform/workspace-wayfinder/docs/formats.md`) | never. Its three files are each its own choice (§1): configure one the repository keeps in the formats or decides to start (its template's skeleton, or the existing file moved into the format), and leave out the others, with their `with:` lines. Without a roadmap there is no Roadmap page and no Milestone line; without a TODO list no Todo page and no `todo` skill; without an architecture document no Architecture page |
| About (`about`) | the manifest | never |
| Features (`features`) | routes the product serves, test files, and `typescript` 5 installed (the test inventory parses with its compiler API, the kit's optional peer) | there is no routed UI; coverage is optional: leave `coverage` out without `json-summary` output. On TypeScript 7 alone, whose package has no compiler API, the test inventory cannot run: leave the area out and say why |
| API (`api`) | an OpenAPI 3 JSON document | there is no such document (the area reads no other format) |
| Platform Docs (`platform-docs`) | plain-language pages, `<order>-<slug>.md` with `title`, `order`, `summary` | there are none and nobody will write them |
| Monitor (`monitor`) | deployed environments and a build-info endpoint, or `mock: true` until it exists | there is nothing deployed |

Each extra area needs its settings (the kit's declarations document every field: `node_modules/@salientform/workspace-wayfinder/dist/settings.d.ts`), its `create…Area` call, its route line in `router.tsx`, its entry in the About manifest, the content collections covering every file it reads, and its registry files, starting empty and valid. What each `create…Area` takes beyond its settings:

| Area | Also needs |
| --- | --- |
| Features | `templates/app/src/features.ts` as is; `productRoutes` (top-level setting) naming the route mirror, `templates/product-routes.json` filled with the product's routes and sidebar paths and covered by a collection; the rules file's `productRoutes` hook to keep the mirror equal to the router; the Vite plugins `featureSources()`, `testInventory()` and, with coverage, `featureCoverage()` |
| API | `apiUrl`, the running API's origin |
| Platform Docs | `product` |
| Monitor | `product`; `variables` for the `{NAME}` placeholders in the environments' URLs |

The About manifest gives each registry its live `count` and owning `date` (`{ name, value }`, the value read from the area's module: the template does so for the reviews and the Audit files, from `AUDIT_AREA.module`); a registry without them shows "—" on its About page. An area the About manifest reads for counts is created in its own module (as `templates/app/src/audit.ts` and `features.ts` are), never in `workspace.tsx`, which imports the manifest: that would be an import cycle.

## 3. Write
1. Install what the app needs, with the repository's package manager: `react`, `react-dom`, `@tanstack/react-router`, `@tanstack/react-query`, `@tanstack/router-core`, `vite`, `@vitejs/plugin-react`, and the kit; with Tailwind (§1), also `tailwindcss` and `@tailwindcss/vite`. Without it, install neither: the app's `styles.css` then imports the kit's compiled `styles.css` and nothing else, and its `vite.config.ts` has no `tailwindcss()` plugin (the `[[with: tailwind]]` lines). A package the repository already has stays at its version. The kit is a release's tarball (the `.tgz` on a GitHub Release of the kit's repository; no registry), committed under `vendor/` and added by that relative path (`pnpm add -D file:vendor/salientform-workspace-wayfinder-<version>.tgz`): pnpm writes the path and the tarball's integrity into `package.json` and the lockfile, so `pnpm install --frozen-lockfile` works in CI and in anything built from the repository, with no token. Commit the tarball with them, and make sure no ignore file of something that builds from the repository drops `vendor/` or `*.tgz` (§1, CI). With pnpm, add the kit to `minimumReleaseAgeExclude` in `pnpm-workspace.yaml` (create it for this setting alone in a single-package repository): pnpm 11 checks the lockfile against its release-age policy on a fresh install (CI, an image build) by asking the registry, which has no such package, and fails. If `wayfinder init` was run before this skill, the kit is already a dev dependency of the root: do not add it again. In a monorepo the app is its own package (`templates/app/package.json.tmpl`) and these are its dependencies (the kit among them, its `file:` path relative to that package; or keep the kit a root dev dependency, beside the skills script that runs it from the root's `node_modules`). In a single-package repository they are the root's dev dependencies (`pnpm add -D`): the workspace is a development tool, so the product's own dependencies do not change.
2. Copy `templates/app/` to `__WS__/` (`src/features.ts` only with Features; `package.json.tmpl` only in a monorepo, where the app is its own package). Copy `workspace.config.mts`, `about-manifest.ts` (and `product-routes.json` with Features) to `__WS__/src/`, and `workspace.rules.mjs` only when a check needs one of its hooks (§2's Features, Platform Docs or API, or a rule of the repository's own), `reviews-index.md` to `docs/reviews/index.md` (or the folder `areas.audit.reviews` names), and, of `ROADMAP.md`, `TODO.md` and `ARCHITECTURE.md`, each one the repository keeps (§2) to `docs/`, unless it already has the file in the format. Fill every placeholder; no `__NAME__` may remain. Make each sentence the templates write true for this repository: an area's `description` in the config (the Readme area's names package READMEs only where there are some; the Audit area's default names only the parts configured, so leave it unset unless it needs the repository's own words), and the About manifest's `holds`. Apply every `[[with: …]]` and `[[without: …]]` marker: keep or delete the line, and leave no marker behind. Keep the `skills` collection's globs under `areas.about.skillsDir`, the real files (Vite's glob does not follow the agent directories' links). Set `skillsDir` and `skillLinks` in the `about` settings only where discovery differs from their defaults.
3. In the root `package.json`: `"wayfinder": { "config": "__WS__/src/workspace.config.mts", "rules": "__WS__/src/workspace.rules.mjs" }` (without a rules file, no `rules`); `"skills:install": "node node_modules/@salientform/workspace-wayfinder/check/install-skills.mjs"`; scripts that run the workspace app (in a monorepo its package's `dev`, `build` and `preview`, through the monorepo tool; in a single-package repository `"workspace:dev": "vite --config __WS__/vite.config.ts"`, `"workspace:build": "vite build --config __WS__/vite.config.ts"` and `"workspace:preview": "vite preview --config __WS__/vite.config.ts"`); and `"workspace:check"`, the checks of the configured areas joined with `&&`, each `node <skillsDir>/<skill>/scripts/<check>.mjs` (from the skills directory, never through an agent directory's link: the About check fails on that):

   | Area | Check script |
   | --- | --- |
   | Audit | `assess-audit/scripts/check-audit-registries.mjs`; with a feature audit, also `assess-feature-audit/scripts/check-features-registry.mjs` |
   | About | `assess-workspace/scripts/check-about.mjs` |
   | Features | `assess-features/scripts/check-feature-catalogue.mjs` |
   | API | `assess-api/scripts/check-api-registry.mjs` |
   | Platform Docs | `assess-platform-docs/scripts/check-platform-docs.mjs` |
   | Readme, Monitor | none |

4. Register the workspace's two ports wherever the repository registers its ports in its own tracked files (its `.env.example`, and `.env` where it keeps one, a ports table in its docs or README). Where its ports appear only in the commands its README lists (`pnpm dev  # http://127.0.0.1:4270`), add the workspace's commands there, each with its port. A register outside the repository, or a file in it that git does not track (untracked or ignored), is not edited: tell the user the two ports and the scripts that serve them, for them to record there. When the repository keeps its ports in its environment, the Vite config passes them, `wayfinder({ settings, repoRoot, ports: { dev, preview } })`, and they win over the config's.
5. Run `skills:install`, on Linux, macOS or WSL: it copies the skills of the configured areas (`assess-workspace` and `wayfinder-onboard` always; `assess-audit`, with `todo` for a TODO list and `assess-feature-audit` for a feature audit; one `assess-*` per other area with a check) into the skills directory, drops a kit skill whose area is no longer configured, and makes, in each `skillLinks` directory, a relative symlink per skill (`.claude/skills/todo` → `../../.agents/skills/todo`), and it refuses to write on any other platform, where a checkout without symlink support turns a link into a text file. Commit the links (git stores a symlink as such), so a clone has them. Git must not ignore them: the installer refuses and the About check fails while it does. Where the repository ignores an agent directory whole (`.claude/` often is, for agents' scratch worktrees), narrow the rule to what stays local (`.claude/worktrees/`, `.claude/settings.local.json`) before installing. Beside each other skill, write a `REPOSITORY.md` only for what this repository needs beyond it: its real paths, its verification commands, its examples. This skill's own `REPOSITORY.md` is always written, in §4: it records the choices of this run.
6. Extend the config for every extra area (§2); add the area's hook to the rules file when the check needs the product's own knowledge (routes, navigation labels, unusual fetch sites).
7. Stage what this run wrote (`git add`) first: the audit check finds markdown files with `git ls-files`, so a file not yet staged has no review asked of it, and the next run of the check asks for it. Then give every tracked markdown file a review under the reviews folder (`<reviews>/<path without .md>.review.md`; a whole directory `<dir>/` gets one at `<reviews>/<dir>/_directory.review.md`, in the format the kit's `docs/formats.md` defines). A review's `kind` is an `id` from the index's `kinds`, the All markdowns section it sits in: with the template's kinds, `spec` and `plan` for the documents in `specDirs` (the first directory specs, the others plans), `config` for agent and tooling configuration (the skills directory, `CLAUDE.md` or `AGENTS.md`, a tool's settings), and `documentation` for every other markdown file (READMEs, guides, decision records, a roadmap or TODO list). Every reviewed file should also be in a `content` collection, or it has no document page (`/audit/document/<path>`) and search does not find it; the audit check does not require it, so check the reviews against the collections: the template's `markdown` collection covers the root's and `docs/`'s markdown, the specs, plans and About prose, and any other reviewed file needs a pattern. The skills directory gets one directory review, `<reviews>/<skillsDir>/_directory.review.md` (`docs/reviews/.agents/skills/_directory.review.md` by default, kind `config`), covering the installed skills and their templates. Give every spec and plan its front matter (`state`, `summary`, and `spec` on a plan); with a roadmap, also its `**Milestone:**` line (without one the line is neither required nor checked).
8. Write the repository's own About prose (`docs/workspace/<name>.md`, the directory `areas.about.prose` names) only where the kit's default (`node_modules/@salientform/workspace-wayfinder/prose/<name>.md`) says something untrue for this repository: read each default for a configured area and for `overview`, `shell` and `skills`. About has no default and needs no file: its pages are the overview, shell and skills prose. A file's `<name>` is `overview`, `shell`, `skills` or the slug of a configured area (`readme`, `audit`, …); any other name fails the About check. It opens with front matter `title` and `summary` (both required), then the page in markdown, as the defaults do. Such a file is tracked markdown like any other: give it a review (step 7, after staging it), and link only to repository paths that exist, since the audit check resolves its links against the repository (another About page is named, not linked).

## 4. Finish
- [ ] The check script passes: every configured area's check prints its OK line.
- [ ] `skills:install --check` reports nothing: the copies are the kit's, one per configured area's skill, and each agent directory links to each of them.
- [ ] The workspace dev server starts on `__PORT__`, and every area and every About page renders.
- [ ] The built workspace works too: the build script (`workspace:build`, or the app package's `build`) succeeds, and the preview (`workspace:preview` on `__PREVIEW_PORT__`) renders every area and every About page with no error in the browser console. The build bundles the content manifest differently from the dev server, so a page can load in one and fail in the other.
- [ ] The app typechecks (`tsc -p __WS__/tsconfig.json`), and whichever of lint, typecheck and tests the repository has still pass.
- [ ] This skill's own `REPOSITORY.md` (beside this file in the skills directory) records what was chosen and why an area or an Audit file was left out, so the next run starts from it; it is covered by the skills directory's review.

## Common Mistakes
| Mistake | Fix |
|---|---|
| Configuring an area with empty or invented data to "have it" | Leave it out; add it when the repository has what it reads |
| Writing a roadmap, TODO list or architecture skeleton the repository will not keep, or configuring a free-form file as one | Leave that Audit file out, with its `[[with: …]]` lines; add it when the repository keeps one in the format |
| A framework default port (5173, 3000, 4173), or a port set in `vite.config.ts` | The config's `ports`, from the repository's own port rules; the workspace throws at load on a default |
| Editing an installed skill | Put the repository's rules in its `REPOSITORY.md`; the About check fails on a changed copy |
| Copying the skills into an agent directory, or leaving one ignored | `skills:install` links them, and the links are committed; the About check fails on a copy where a link belongs, and on an ignored link |
| A `workspace:check` step through an agent directory (`node .claude/skills/…`) | `node <skillsDir>/…`, the installed copy; the About check fails on the link's path |
| Writing a path in the config that the content collections do not cover | Every file an area reads is in a `content` collection; the workspace throws at load otherwise |
| Leaving markdown out of the reviews | Every tracked markdown file has a review, or the audit check fails |
| A review under a dot-directory no glob covers | A glob enters a dot-directory only where its pattern names one: add a pattern naming it to the content collection, or the audit check fails |
| Creating an area the manifest reads in `workspace.tsx` | Its own module, so the manifest can import it without a cycle |
