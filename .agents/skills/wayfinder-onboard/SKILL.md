# Wayfinder Onboard

Read `REPOSITORY.md` beside this file first, if it exists: it holds this repository's own rules for this skill, and they take precedence over the examples here.

## How this skill arrives
In a repository that does not run Wayfinder yet, this skill is installed by the kit's command: `pnpm add -D file:vendor/<tarball>` (a release's tarball, committed under `vendor/`: §3 step 1), then `pnpm exec wayfinder init` at the repository root. `init` installs this skill alone into the skills directory (`.agents/skills`, or its `--skills-dir`) and links it from `.claude/skills`. This run adds the root script `skills:install` (`node node_modules/@salientform/workspace-wayfinder/check/install-skills.mjs`, §3 step 3) and runs it to install the other skills (§3 step 5). Once the root `package.json` names `wayfinder.config`, `wayfinder init` installs nothing and points at that script, which owns the skills from then on. A repository that runs Wayfinder already uses this skill when an area becomes a placeholder or stops being one (an area's own skill fills its placeholder, §2).

## Overview
Workspace Wayfinder is an engineering workspace a repository runs as its own small Vite app: areas for the roadmap and specs (Audit), READMEs, a feature catalogue, an API reference and plain-language docs, each built from the repository's files at build time and kept true to the code by skills and check scripts. This skill fits it to one repository. It assumes JavaScript or TypeScript with Vite, and Node 22.18 or later (the checks load the `.mts` config directly). It asks before anything it cannot discover.

The onboarding has two steps. **Write** (§3): the app, the config with every area, the hooks file, the document set and the reviews. **First runs** (§4): each area's skill on its first run, which builds the area's registry from nothing and derives its detailed settings from the repository; `assess-workspace` comes last and builds the About manifest. No registry is written by hand or copied from another repository, and no template holds one.

`scripts/propose.mjs` beside this file reads, from the repository alone, what §1 can find without judgement: the product's name and the workspace's title, the repository's https URL (an SSH host alias resolved through `ssh -G`), the id prefix to suggest, and the Readme area's sections and collection. Run it first (`node <skillsDir>/wayfinder-onboard/scripts/propose.mjs`, where `wayfinder init` installed this skill); it prints a table of each setting it proposes and where it read it, and what it leaves to you (the branch, the ports, the header links). Two runs agree, so the values are the repository's, not a guess.

The templates beside this file (`templates/`) are the files to write. A `.tmpl` suffix (on the app's `package.json`, `tsconfig.json` and `vite.config.ts`, so no tool mistakes the templates for a project) is dropped when the file is written. `__NAME__` placeholders are filled from discovery:

| Placeholder | Means |
| --- | --- |
| `__PRODUCT__` | the product's name as its users know it |
| `__REPO_URL__`, `__BRANCH__` | the repository host's https URL (no trailing slash) and the branch links point at |
| `__WS__` | the workspace app's directory, repository-relative (`workspace`, or `apps/workspace` in a monorepo) |
| `__PACKAGE_NAME__` | the workspace app's package name, in a monorepo (`@acme/workspace`) |
| `__TO_ROOT__` | the path from `__WS__` back to the root (`..`, `../..`) |
| `__PORT__`, `__PREVIEW_PORT__` | the workspace dev server's and preview server's ports (the config's `ports`), assigned in §1 |
| `__TODAY__` | today, `YYYY-MM-DD` |
| `__ID_PREFIX__` | the prefix every roadmap and TODO id carries (`areas.audit.idPrefix`): upper-case letters and digits, starting with a letter. Suggest the initials of the repository's name, as `suggestIdPrefix` in the kit's `check/audit-markdown.mjs` makes them (`workspace-wayfinder` → `WW`, `acme-billing-api` → `ABA`, one word → its first three letters), and ask the user to confirm it: it is in every id from then on |

A template line ending in a marker comment, `[[with: <part>]]` (`/* [[with: tailwind]] */`, `// [[with: tailwind]]`), belongs to an optional part: keep the line, without the comment, when the repository has that part (§1), and delete it when it does not. A `[[without: <part>]]` line is the other way round: kept, without the comment, only when the repository does not have the part. The one part is Tailwind v4 in the app, `[[with: tailwind]]` and `[[without: tailwind]]`. Only markers use `[[`, so once the files are written `grep -rn '\[\[with' <written files>` (and `\[\[without`) must find nothing.

The documents are not among these templates: the `document-repo` skill writes the whole document set (§3 step 7), the roadmap, the TODO list and the architecture document among them, from its own templates.

## 1. Discover
Read, do not guess. Record each answer; they become the config.

| Question | Where to look | Decides |
| --- | --- | --- |
| Package manager, monorepo tool, workspaces | root `package.json` (`packageManager`, `workspaces`), `pnpm-workspace.yaml`, `nx.json`, `turbo.json` | install commands, `__WS__`, whether the app is its own package |
| Name, host URL | `package.json`; `git remote get-url origin`, written as https (`git@host:org/repo.git` → `https://host/org/repo`). The host of an SSH remote may be an alias from `~/.ssh/config` (`git@work-github:org/repo.git`): its real name is the `hostname` line of `ssh -G <alias>`; ask when that does not settle it | `__PRODUCT__`, `__REPO_URL__`, `__ID_PREFIX__` (from the repository's name) |
| Branch | the branch work integrates into (where specs and plans merge), which can differ from `origin/HEAD`: ask when unsure | `__BRANCH__` |
| Ports | the repository's port rules (a port block, `.env`, a ports table), and the machine's port ledger where the agent's instructions or the repository's point to one, read for the ports already taken and for how a project's ports are recorded (§3 step 4) | `ports`: two ports, suggested to the user and assigned once they agree, never a framework default (3000, 3001, 4173, 4200, 5000, 5173, 8000, 8080). The suggestion comes from the first of these that exists: (1) the repository's own port rules, two free ports in its range; (2) a port ledger for the machine, which the agent's instructions or the repository's point to (a table or file of port blocks by project), two free ports in the block it assigns this repository, or, when it assigns none, the next free block, named for the user to reserve there; (3) neither: two consecutive ports between 20000 and 32767, below most systems' ephemeral range, outside every block a ledger reserves. Every suggested port is free now: nothing listens on it (`ss -tlnp`, `lsof -iTCP -sTCP:LISTEN` or `netstat -an`, whichever the machine has, and `docker ps` for published ports). The ledger informs the suggestion only: the workspace runs on whatever ports the config holds |
| Other apps | the repository's other front ends (the product, a design system, docs) and their dev ports and deployed paths | `links`, the header's links to them (optional): a `label` and the app's dev `port`, and a `path` only where a build serves the app beside the workspace on one origin (without one, a build under a base shows no link). The kit has no Design System area: a repository's design system is its own app, which `links` can point at |
| READMEs | the root README, package or library READMEs and how they group (`libs/`, `packages/`) | the `readmes` collection, `areas.readme.sections` |
| Tailwind | whether the repository uses Tailwind v4: `tailwindcss` 4 in a `package.json`, `@import 'tailwindcss'` in a stylesheet, `@tailwindcss/vite` in a Vite config | the part `tailwind`: with it, the app's `styles.css` compiles the kit's classes with Tailwind and the app's theme; without it, the app imports the kit's compiled stylesheet and installs no Tailwind |
| Theme | whether the repository's apps have a theme system of their own: a theme provider, a light and dark control, a class or attribute it sets on `<html>` | who sets the workspace's theme. Without one (the default), the kit does: `main.tsx` calls `startTheme()` before it renders and the header shows the kit's `ThemeToggle` (both from `@salientform/workspace-wayfinder/theme`), which follows the reader's system setting until they choose and remembers the choice. With one, the app renders that provider, sets the kit's `dark` class on `<html>` from it and passes the repository's own control as `headerActions`, so the workspace changes theme with the product; the template's two kit lines go (§3 step 2) |
| Router and navigation | the router setup (route tree, file routes), the sidebar or nav component | the hooks file's `productRoutes` (a TanStack Router `createRoute` tree reads with the kit's `tanstackRoutes`, `check/route-readers.mjs`) and `navLabels`, from which `assess-features` builds the route mirror (§4) |
| API | an OpenAPI 3 **JSON** document, or the command that emits one; where the product calls the API | the API area, `areas.api.generated`, `areas.api.callers` |
| CI | the repository's CI workflows, and whether anything that builds from the repository ignores `vendor/` or `*.tgz` (`.dockerignore`, a deploy tool's ignore file) | ask the user whether CI should run the check script (the committed tarball installs there: §3 step 1), and record the answer in this skill's `REPOSITORY.md` |
| Tests and coverage | test runners (Vitest, Playwright, `node:test`), test globs, coverage output (`json-summary`) | whether Features can be generated; `assess-features`' first run derives `areas.features.tests` and `coverage` (§4) |
| Docs | the specs and plans directories (none yet: keep the defaults, `docs/specs` and `docs/plans`; the audit check accepts directories that do not exist yet, and a spec written there later is read); plain-language product docs; the repository's own records of the kind the document set holds: a roadmap or list of planned work, a TODO list, an architecture document, a setup guide, a list of known issues, in any shape and anywhere (a root `TODO.md`, a README section) | `specDirs`, Platform Docs; the sources `document-repo` reads in §3 step 7, which moves each into `docs/` in the kit's format (`docs/formats.md`) |
| Source layout | the source roots, entry files, libraries whose exports are a public API | the first runs of `assess-features` (`sourceRoots`) and `assess-feature-audit` (`unusedExports`) derive them (§4) |
| Skills directory | where the kit's skills are installed: `.agents/skills` by default, the agent-neutral directory Codex and opencode read; another only when the repository already keeps its agent skills in one that every agent it uses reads | `areas.about.skillsDir`, the `skills` collection's globs |
| Agents | which coding agents the repository's people use (ask); where each reads skills (Claude Code `.claude/skills`; Codex `.agents/skills`, from the working directory up to the repository root; opencode `.opencode/skills`, `.claude/skills` and `.agents/skills`); whether git ignores each such directory (`git check-ignore -q <dir>/x`), and what for | `areas.about.skillLinks`: every agent directory that does not read the skills directory, each getting a link per kit skill (default `['.claude/skills']`, for Claude Code; `[]` when every agent reads the skills directory); for an ignored one, the narrower `.gitignore` rule in §3 |

## 2. Every area is present
All six areas are in every workspace, in the templates' header order. Readme, Audit and About are always generated. Each of the other three is generated when the repository has what it reads, and otherwise is a **placeholder**: its settings are `{ placeholder: { reason, toFill } }`, two sentences saying what was looked for and not found, and what would fill it (a file to add, a decision to make, a skill to run). Its page shows them under the area's description; its check passes and prints them (§3 step 3); About's Placeholders page lists them. Never leave an area out: the About check fails on a missing one. Never configure an area with empty or invented data to "have it": that is what the placeholder is for.

| Area | Generated when the repository has | Otherwise |
| --- | --- | --- |
| Readme Index (`readme`) | READMEs | always generated |
| Audit (`audit`) | the reviews folder, each spec's and plan's front matter, and the roadmap, the TODO list and the architecture document in the kit's formats (`node_modules/@salientform/workspace-wayfinder/docs/formats.md`), all three required and written by `document-repo` (§3 step 7) | always generated. A repository with no planned work, no TODO list or nothing to say about a section still gets the file, with a placeholder that says why. Without a feature audit (`featureAudit`), Audit's Features page is a placeholder the kit states |
| About (`about`) | the manifest | always generated |
| Features (`features`) | routes the product serves and test files | a placeholder. With routes but no test files, the area is generated with `tests: { placeholder }`; without `json-summary` coverage output, leave `coverage` out and the kit shows its coverage as a placeholder |
| API (`api`) | an OpenAPI 3 JSON document | a placeholder (the area reads no other format) |
| Platform Docs (`platform-docs`) | plain-language pages, `<order>-<slug>.md` with `title`, `order`, `summary`; or a product UI with navigation to describe, from which `assess-platform-docs`' first run drafts a page per navigation item (§4) | a placeholder (no product UI) |

The templates write the four as placeholders with general reasons: make each reason true for this repository (say what was looked for, and where), or replace the placeholder with the area's settings. A generated area needs its settings (the kit's declarations document every field: `node_modules/@salientform/workspace-wayfinder/dist/settings.d.ts`), the content collections covering every file it reads, and its registry files: the area's skill writes all three on its first run (§4), from the repository. The app's `create…Area` call, route line and Vite plugins are the same for both forms, so only the config and the About manifest change. What each `create…Area` takes beyond its settings:

| Area | Also needs |
| --- | --- |
| Features | `templates/app/src/features.ts` as is, and the Vite plugins `featureSources()`, `testInventory()` and `featureCoverage()` (both always written); generated, also `productRoutes` (top-level setting) naming the route mirror, which `assess-features`' first run writes from the hooks file's `productRoutes` hook (no template holds it), covered by a collection |
| API | generated, optionally `apiUrl`, the running API's origin |
| Platform Docs | `product` |

The About manifest (`__WS__/src/about-manifest.ts`) is built, never written: `assess-workspace`'s first run builds it whole from the config and the installed skills, last (§4), and the About check fails while it differs from a fresh build. It has an entry per area, a placeholder area's empty, and gives each registry its live `count` and owning `date`, read from the area's module. An area the manifest reads for counts is created in its own module (as `templates/app/src/audit.ts` and `features.ts` are), never in `workspace.tsx`, which imports the manifest: that would be an import cycle.

## 3. Write
1. Install what the app needs, with the repository's package manager: `react`, `react-dom`, `@tanstack/react-router` (it brings its own `@tanstack/router-core`: do not add that), `vite`, `@vitejs/plugin-react`, and the kit; with Tailwind (§1), also `tailwindcss` and `@tailwindcss/vite`. Without it, install neither: the app's `styles.css` then imports the kit's compiled `styles.css` and nothing else, and its `vite.config.ts` has no `tailwindcss()` plugin (the `[[with: tailwind]]` lines). A package the repository already has stays at its version. The kit is a release's tarball (the `.tgz` on a GitHub Release of the kit's repository; no registry), committed under `vendor/` and added by that relative path (`pnpm add -D file:vendor/salientform-workspace-wayfinder-<version>.tgz`): pnpm writes the path and the tarball's integrity into `package.json` and the lockfile, so `pnpm install --frozen-lockfile` works in CI and in anything built from the repository, with no token. Commit the tarball with them, and make sure no ignore file of something that builds from the repository drops `vendor/` or `*.tgz` (§1, CI). With pnpm, add the kit to `minimumReleaseAgeExclude` in `pnpm-workspace.yaml` (create it for this setting alone in a single-package repository): pnpm 11 checks the lockfile against its release-age policy on a fresh install (CI, an image build) by asking the registry, which has no such package, and fails. If `wayfinder init` was run before this skill, the kit is already a dev dependency of the root: do not add it again. In a monorepo the app is its own package (`templates/app/package.json.tmpl`) and these are its dependencies (the kit among them, its `file:` path relative to that package; or keep the kit a root dev dependency, beside the skills script that runs it from the root's `node_modules`). In a single-package repository they are the root's dev dependencies (`pnpm add -D`): the workspace is a development tool, so the product's own dependencies do not change.
2. Copy `templates/app/` to `__WS__/` (`package.json.tmpl` only in a monorepo, where the app is its own package). Copy `workspace.config.mts` to `__WS__/src/`, and `workspace.hooks.mjs` when the product has a UI with routes or navigation (the first runs of Features and Platform Docs, §4, read them through its hooks), calls an API from places a script cannot find (`fetchSites`), or the repository has a check of its own; remove it at §5 if no hook was written, and `reviews-index.md` to `docs/reviews/index.md` (or the folder `areas.audit.reviews` names). The documents come in step 7; the About manifest and every registry in §4. Fill every placeholder, from `scripts/propose.mjs` where it proposes the value; no `__NAME__` may remain. Keep the template's theme wiring (`startTheme()` in `main.tsx`, `headerActions: <ThemeToggle />` in `workspace.tsx`) unless the repository has a theme system of its own (§1): then delete both lines and their imports, wrap the shell in the repository's theme provider in `main.tsx`, have it set the `dark` class on `<html>` (the kit's dark convention), and pass the repository's own control as `headerActions`, so the two never disagree. Make each sentence the templates write true for this repository: an area's `description` in the config (the Readme area's names package READMEs only where there are some; leave the Audit area's unset unless it needs the repository's own words). The Audit area's `phaseKinds`, `todoAreas` and `todoSources` keep the template's values until `assess-audit`'s first run (§4) reads them off the documents step 7 writes: until then the audit check fails on any phase kind or TODO area the documents use that the template does not list (`area "core" is not one of app | docs | repo`). That is expected; the first run clears it. Apply every `[[with: …]]` and `[[without: …]]` marker: keep or delete the line, and leave no marker behind. Keep the `skills` collection's globs under `areas.about.skillsDir`, the real files (Vite's glob does not follow the agent directories' links). Set `skillsDir` and `skillLinks` in the `about` settings only where discovery differs from their defaults.
3. In the root `package.json`: `"wayfinder": { "config": "__WS__/src/workspace.config.mts", "hooks": "__WS__/src/workspace.hooks.mjs" }` (without a hooks file, no `hooks`); `"skills:install": "node node_modules/@salientform/workspace-wayfinder/check/install-skills.mjs"`; scripts that run the workspace app (in a monorepo its package's `dev`, `build` and `preview`, through the monorepo tool; in a single-package repository `"workspace:dev": "vite --config __WS__/vite.config.ts"`, `"workspace:build": "vite build --config __WS__/vite.config.ts"`, `"workspace:preview": "vite preview --config __WS__/vite.config.ts"` and `"workspace:typecheck": "tsc -p __WS__/tsconfig.json"`, §5's typecheck); and `"workspace:check"`, every check below joined with `&&`, placeholder areas' included, each `node <skillsDir>/<skill>/scripts/<check>.mjs` (from the skills directory, never through an agent directory's link: the About check fails on that). A placeholder area's check passes and prints its placeholder; every check prints the placeholders it owns after its OK line (`placeholder: <where> — <reason> To fill: <what>`) and fails on them only when run with `--strict`:

   | Area | Check script |
   | --- | --- |
   | Audit | `assess-audit/scripts/check-audit-registries.mjs`; and `assess-feature-audit/scripts/check-features-registry.mjs` right after it, added by that skill's first run (§4), which writes the feature audit it checks |
   | About | `assess-workspace/scripts/check-about.mjs` |
   | Every repository | `document-repo/scripts/check-documents.mjs`, the document set |
   | Features | `assess-features/scripts/check-feature-catalogue.mjs` |
   | API | `assess-api/scripts/check-api-registry.mjs` |
   | Platform Docs | `assess-platform-docs/scripts/check-platform-docs.mjs` |
   | Readme | none |

   **With a task runner that caches or skips tasks by their inputs** (Nx, Turborepo, or any other, §1): the workspace's build and its checks read files outside the app's folder, which such a runner does not count as the app's inputs by default: the documents and READMEs the content collections name, the reviews folder, the registries, the skills directory, the workspace config and the hooks file, and the root `package.json`. Declare them as inputs of the workspace's build, preview, test and check tasks in the runner's own configuration (every path the config's `content` collections and `areas` name, plus the config itself), or leave those tasks uncached. Otherwise a change to a document alone is served from the cache: the build looks green and shows the old page. Record which was done in this skill's `REPOSITORY.md`.

4. Record the workspace's two ports in the machine's port ledger, where §1 found one: the table or file of port blocks by project that the agent's instructions or the repository's point to, with its own rules for how a project's ports are added to it (an entry in a file it reads, often a manifest in the repository; a command that regenerates the table from those files). Follow those rules: add the two ports, each with what serves it (the workspace's dev server, its preview), where the ledger says this repository's ports go. A ledger file outside the repository, or one git does not track, is not edited: tell the user the two ports, what serves them and the ledger's own step for recording them. With no port ledger found, skip this step. When the repository keeps its ports in its environment, the Vite config passes them, `wayfinder({ settings, repoRoot, ports: { dev, preview } })`, and they win over the config's.
5. Run `skills:install`, on Linux, macOS or WSL: it copies all nine kit skills into the skills directory, whatever the areas (an area's skill is what fills its placeholder), and makes, in each `skillLinks` directory, a relative symlink per skill (`.claude/skills/todo` → `../../.agents/skills/todo`), and it refuses to write on any other platform, where a checkout without symlink support turns a link into a text file. Commit the links (git stores a symlink as such), so a clone has them. Git must not ignore them: the installer refuses and the About check fails while it does. Where the repository ignores an agent directory whole (`.claude/` often is, for agents' scratch worktrees), narrow the rule to what stays local (`.claude/worktrees/`, `.claude/settings.local.json`) before installing. Each area skill's first run (§4) writes its `REPOSITORY.md`, opening with its proposal's table. Beside `todo` and `document-repo`, which have no first run, write one only for what this repository needs beyond the skill: its real paths, its verification commands, its examples. This skill's own `REPOSITORY.md` is always written, in §5: it records the choices of this run.
6. Make the config true for every area (§2): a placeholder's reason and what would fill it, where the repository has nothing for the area. An area it can support stays a placeholder until its skill's first run (§4) replaces it with the settings it derives. Write the hooks a generated area needs (the product's routes, navigation labels, unusual fetch sites) in the hooks file: the first runs read them.
7. Run the `document-repo` skill, installed by step 5, over the repository: it writes the eight documents of the document set in `docs/` (about, skills, architecture, roadmap, features, TODO, setup, issues), each from what the repository already says, with a placeholder for whatever it cannot find, and moves an existing record of the same kind (§1, Docs) into the format rather than leaving a second copy. The three the Audit area reads are at the paths `areas.audit` names. Its check, `check-documents.mjs`, prints its OK line. The audit check still fails here, expectedly: on the reviews step 8 writes, and, where the TODO list or the roadmap was moved from the repository's own, on each entry's `Area` and phase's `Kind` the template's `todoAreas` and `phaseKinds` do not list (step 2); `assess-audit`'s first run (§4) proposes both lists from the documents and clears them. Anything else it reports about the three is the document's to fix (a roadmap with no planned work holds the placeholder under its Sequence; the architecture document has all six sections). Do not write a document from a skeleton here: the skill's own templates and rules apply. `FEATURES.md` is written once the Features area's first run has settled whether there is a catalogue (§4, the second `document-repo` pass): here it is a placeholder file (`document-repo`'s `templates/PLACEHOLDER.md`).
8. Stage what this run wrote (`git add`, the kit's tarball under `vendor/` included) first: the audit check finds markdown files with `git ls-files`, so a file not yet staged has no review asked of it, and the next run of the check asks for it. Then give every tracked markdown file a review under the reviews folder (`<reviews>/<path without .md>.review.md`; a whole directory `<dir>/` gets one at `<reviews>/<dir>/_directory.review.md`, in the format the kit's `docs/formats.md` defines). A review's `kind` is an `id` from the index's `kinds`, the All markdowns section it sits in: with the template's kinds, `spec` and `plan` for the documents in `specDirs` (the first directory specs, the others plans), `config` for agent and tooling configuration (the skills directory, `CLAUDE.md` or `AGENTS.md`, a tool's settings), and `documentation` for every other markdown file (READMEs, guides, decision records, a roadmap or TODO list). Every reviewed file should also be in a `content` collection, or it has no document page (`/audit/document/<path>`) and search does not find it; the audit check does not require it, so check the reviews against the collections: the template's `markdown` collection covers the root's and `docs/`'s markdown, the specs, plans and About prose, and any other reviewed file needs a pattern. The skills directory gets one directory review, `<reviews>/<skillsDir>/_directory.review.md` (`docs/reviews/.agents/skills/_directory.review.md` by default, kind `config`), covering the installed skills and their templates. Give every spec and plan its front matter (`state`, `summary`, and `spec` on a plan) and its `**Milestone:**` line, naming the roadmap phase step 7 gave it (or an X id under Outside the roadmap).
9. Write the repository's own About prose (`docs/workspace/<name>.md`, the directory `areas.about.prose` names) only where the kit's default (`node_modules/@salientform/workspace-wayfinder/prose/<name>.md`) says something untrue for this repository: read each default for an area and for `overview`, `shell` and `skills`. About has no default and needs no file: its pages are the overview, shell and skills prose. A file's `<name>` is `overview`, `shell`, `skills` or the slug of an area (`readme`, `audit`, …); any other name fails the About check. It opens with front matter `title` and `summary` (both required), then the page in markdown, as the defaults do. Such a file is tracked markdown like any other: give it a review (step 8, after staging it), and link only to repository paths that exist, since the audit check resolves its links against the repository (another About page is named, not linked).

## 4. First runs
Run each area's skill on its first run, in this order, so each reads what the one before wrote. Each skill's "First run" section says how, in two parts: build its registry from nothing, and derive its area's detailed settings into the config. Its `scripts/propose.mjs` prints the settings a script can read off the repository without judgement, as a table, and `--write` writes the registries a script can build or draft; the skill writes the settings into the config, judges the rest, and opens its `REPOSITORY.md` with the table, followed by what it judged and why. Keep the table the proposal prints on its first run, before `--write` and before its settings are in the config: it is what `REPOSITORY.md` opens with. A proposal with no settings to print (Platform Docs drafting its first pages, an area that stays a placeholder) prints its summary and notes instead: open `REPOSITORY.md` with those, and with the placeholder's reason where the area stays one. Stage the markdown each first run writes (the feature catalogue, the Platform Docs pages) and review it as §3 step 8 says, a folder of them by one directory review, or the audit check asks for each. The app loads again only once `assess-workspace` has run, last: until it widens the content collections, a page that reads a new file finds none, so use each skill's check, not the app, in between. An existing registry, About manifest, feature page or review is neither kept nor read (the first run proves what the kit can build); the repository's own records are, as `document-repo` reads them (§3 step 7).

An area its skill finds nothing for stays a placeholder: the skill makes the reason true (what was looked for, and where). A generated area joins the check script (§3 step 3) with its check. ## Hosted in the kit's repository
In the kit's own checkout, this skill can also build an instance for another repository without changing it: a hosted
workspace (the kit's `docs/specs/2026-11-20-hosted-workspaces-design.md`). `pnpm hosted new <name> <repository>`, from
the kit's root, makes `.workspaces/<name>/`, a folder that reads as that repository with the instance installed: it
holds a copy of each of the repository's files, a copy of the kit's skills at the skills directory (`.agents/skills`,
or `--skills-dir`) and a link to the kit's working copy at `node_modules/@salientform/workspace-wayfinder`. Run §1 to
§5 with that folder as the repository's root, with these differences:

- **Write the folder, never the repository.** Every file in the folder is a copy, so write and edit there as in a
  repository: nothing reaches the repository. A copy you change (a spec's missing `**Milestone:**` line, say) is the
  instance's own from then on, and a refresh leaves it alone; delete it to have the repository's copy back. A move
  (`document-repo` moving a root `TODO.md` into `docs/`) is the file at the new path and the old path in the folder's
  `hide`. Never edit a kit skill's copy: the About check fails on it, as in a repository.
- **Hide what the instance replaces whole.** Where the repository already runs Wayfinder, list its install in the
  folder's `.wayfinder-hosted.json` `hide` (its app folder, its reviews folder, its About prose, its agent directories'
  links), then run `pnpm hosted refresh <name>`: its files are the old install's output, never this run's input. In
  `package.json`, drop the old install's `wayfinder` key, its scripts (`skills:install`, `workspace:*`) and its
  dependency on the kit's tarball.
- **Copy what an area reads that git ignores.** The folder copies what git lists. Coverage summaries, and any other
  ignored file the config names, go in the folder's `include` (globs), then `pnpm hosted refresh <name>`.
- **§1.** Discover through the folder. Git fails inside it: ask git about the repository (its remote, its branch)
  with `git -C <repository>`. The repository's port rules do not apply: the instance serves on the kit's.
- **§3 step 1.** Install nothing: the app's packages are the kit's own, and the kit is its working copy.
- **§3 step 3.** In `package.json`, add `wayfinder` and the check script as in a repository. Add no
  `skills:install` and no app scripts: the kit's own `workspace:dev`, `:build`, `:preview` and `:typecheck` run the
  instance with `WAYFINDER_WORKSPACE=<name>`.
- **§3 step 4.** The ports are the kit's pair for a hosted instance, `4284` and `4285`. Register nothing in the
  repository.
- **§3 step 5.** No `skills:install`: the kit's skills are already copied, and every refresh brings them up to date with
  the working copy. `areas.about.skillsDir` is the folder's `skillsDir`, and `skillLinks` is `[]` (an agent in the
  kit's checkout reads the kit's own `.claude/skills`). A skill's `REPOSITORY.md` is the instance's own.
- **§3 step 7.** `SKILLS.md` says the kit's skills are copied from the kit's working copy, not installed by
  `skills:install`.
- **§3 step 8.** Stage nothing: every file of the instance's own counts as tracked.
- **Running it.** From the kit's root, after `pnpm build`: `pnpm hosted check <name>` runs the instance's own check
  script, and `WAYFINDER_WORKSPACE=<name>` before `pnpm workspace:typecheck`, `:build`, `:dev` (on `4284`) or
  `pnpm test:e2e` runs the kit's on the instance; each refreshes the copies first (a dev server sees the repository's
  later edits after `pnpm hosted refresh <name>` and a restart). A skill's script runs inside the folder
  (`node .agents/skills/<skill>/scripts/propose.mjs`), or from the kit's root with the variable.
- **Commit nothing.** `.workspaces/` is ignored by the kit's git: the instance stays in this checkout.
- **§5.** One more item: `git -C <repository> status` shows nothing this run made.

## Common Mistakes
| Mistake | Fix |
|---|---|
| Configuring an area with empty or invented data to "have it", or leaving an area out | Every area is in `areas`: one the repository cannot support is a placeholder whose reason says what was looked for |
| Writing a registry, a detailed setting or the About manifest by hand, or copying one from another repository | The area's skill builds it on its first run (§4), from its `propose.mjs` and its own judgement |
| A first run that reads the registry an earlier install left | It is the kit's output, not a source: build afresh, and list the differences where the repository keeps a reference |
| A template placeholder's general reason left as written | Make it true for this repository: what was looked for, and where |
| Writing the roadmap, the TODO list or the architecture document by hand, or leaving the repository's own list in another shape beside it | `document-repo` writes them (§3 step 7) and moves the existing record into the format |
| Leaving out the roadmap, the TODO list or the architecture document because the repository has nothing for it | All three are required: the file holds a placeholder that says what was looked for |
| A framework default port (5173, 3000, 4173), or a port set in `vite.config.ts` | The config's `ports`, from the repository's own port rules; the workspace throws at load on a default |
| Editing an installed skill | Put the repository's rules in its `REPOSITORY.md`; the About check fails on a changed copy |
| Copying the skills into an agent directory, or leaving one ignored | `skills:install` links them, and the links are committed; the About check fails on a copy where a link belongs, and on an ignored link |
| A `workspace:check` step through an agent directory (`node .claude/skills/…`) | `node <skillsDir>/…`, the installed copy; the About check fails on the link's path |
| Writing a path in the config that the content collections do not cover | Every file an area reads is in a `content` collection; the workspace throws at load otherwise |
| Leaving markdown out of the reviews | Every tracked markdown file has a review, or the audit check fails |
| A review under a dot-directory no glob covers | A glob enters a dot-directory only where its pattern names one: add a pattern naming it to the content collection, or the audit check fails |
| The kit's `ThemeToggle` beside a theme system of the repository's own | One owner of the `dark` class: the repository's provider and its control in `headerActions`, with no `startTheme()` and no `ThemeToggle` |
| A task runner that caches the workspace's build by the app folder alone | Declare the files the workspace reads outside it as the task's inputs, or leave the task uncached (§3 step 3); a docs-only change must rebuild |
| Creating an area the manifest reads in `workspace.tsx` | Its own module, so the manifest can import it without a cycle |
